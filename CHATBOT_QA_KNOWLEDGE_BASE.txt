ชุดข้อมูลความรู้สำหรับสอน CHATBOT (Q&A KNOWLEDGE BASE - 50 ข้อแบบเจาะลึก)
==============================================================================


ระบบขออนุมัติเข้าใช้ห้องปฏิบัติการสาขาวิชาวิศวกรรมโยธานอกเวลาปฏิบัติงาน (CE F.A.I.R.)
================================================================================

[หมวดหมู่ 1: วัตถุประสงค์และขอบเขตของระบบ]
Q1: ระบบนี้คือระบบอะไร และมีวัตถุประสงค์เพื่ออะไร?
A1: ระบบนี้มีชื่อว่า CE F.A.I.R. เป็นระบบดิจิทัลสำหรับยื่นคำขอและพิจารณาอนุมัติเข้าใช้งานห้องปฏิบัติการสาขาวิชาวิศวกรรมโยธา คณะวิศวกรรมศาสตร์ มหาวิทยาลัยขอนแก่น ในช่วงนอกเวลาทำการ เพื่อยกระดับความปลอดภัย ความโปร่งใส ตรวจสอบได้แบบไร้กระดาษ 100%

Q2: ใครบ้างที่มีสิทธิ์ยื่นคำขอใช้งานห้องปฏิบัติการผ่านระบบนี้?
A2: ผู้มีสิทธิ์ยื่นคำขอประกอบด้วย 3 กลุ่มหลัก ได้แก่ 1. นักศึกษา (ระดับปริญญาตรี ปริญญาโท และปริญญาเอก) 2. บุคลากรสายวิชาการและสายสนับสนุน 3. บุคคลภายนอกหรือนักศึกษาต่างสถาบัน/ต่างคณะที่มีโครงการวิจัยร่วมกับสาขาวิชา

Q3: ระบบนี้รองรับการใช้งานบนอุปกรณ์ใดบ้าง?
A3: ระบบถูกพัฒนาแบบ Responsive Web Application สามารถใช้งานได้สมบูรณ์บนคอมพิวเตอร์ แท็บเล็ต และสมาร์ทโฟนทุกระบบปฏิบัติการ (iOS / Android / Windows / macOS) ผ่านเว็บบราวเซอร์ เช่น Google Chrome, Safari, Microsoft Edge

--------------------------------------------------------------------------------
[หมวดหมู่ 2: ช่วงเวลาและเงื่อนไขการใช้งานนอกเวลา]
Q4: ช่วงเวลานอกเวลาทำการที่สามารถขอเข้าใช้งานได้คือช่วงเวลาใด?
A4: 1. วันจันทร์ - ศุกร์: ช่วงเวลา 16.30 น. ถึง 20.30 น.
2. วันเสาร์ - อาทิตย์ และวันหยุดนักขัตฤกษ์: ช่วงเวลา 08.30 น. ถึง 16.30 น. (กรณีมีความจำเป็นพิเศษสามารถระบุเหตุผลในคำขอเพื่อให้อาจารย์และหัวหน้าห้องแล็บพิจารณา)

Q5: สามารถขอใช้งานห้องปฏิบัติการข้ามคืน (Overnight) ได้หรือไม่?
A5: ตามระเบียบความปลอดภัย ไม่อนุญาตให้เปิดปฏิบัติงานตลอดทั้งคืน เว้นแต่การทดสอบตัวอย่างระยะยาวที่เครื่องจักรทำงานอัตโนมัติ โดยต้องระบุในคำขอและได้รับความเห็นชอบเป็นลายลักษณ์อักษรจากหัวหน้าห้องปฏิบัติการและหัวหน้าอาคาร

Q6: ระยะเวลาการได้รับอนุญาตต่อ 1 คำขอนานเท่าใด?
A6: ค่าเริ่มต้นที่ระบบอนุญาตคือ 3 เดือน (สามารถขยายเวลาได้ตามการพิจารณาของหัวหน้าตึก/ผู้ดูแลระบบเมื่อสิ้นสุดระยะเวลา)

--------------------------------------------------------------------------------
[หมวดหมู่ 3: กฎเหล็กด้านความปลอดภัยและการร่วมปฏิบัติงาน]
Q7: สามารถเข้าใช้งานห้องปฏิบัติการเพียงคนเดียว (Lone Working) ได้หรือไม่?
A7: "ไม่อนุญาตเด็ดขาด" ตามมาตรการ Safety First ผู้ปฏิบัติงานต้องมีผู้ร่วมใช้งาน (Companion) อยู่ในห้องแล็บด้วยอย่างน้อย 1 คนเสมอ และต้องกรอกชื่อ-สกุลของผู้ร่วมงานลงในแบบฟอร์มคำขอ

Q8: หากเกิดเหตุฉุกเฉินในห้องปฏิบัติการนอกเวลา ต้องทำอย่างไร?
A8: 1. กดสัญญาณเตือนภัยหรือแจ้งผู้ร่วมปฏิบัติงานทันที 2. ติดต่อผู้ดูแลอาคารหรือเบอร์ฉุกเฉินที่ระบุไว้บนป้ายหน้าห้อง 3. ติดต่อบุคคลที่ระบุในช่อง Emergency Contact ของคำขอ 4. ระงับเหตุเบื้องต้นด้วยอุปกรณ์ความปลอดภัยตามมาตรฐานห้องแล็บ

Q9: การแต่งกายที่ถูกต้องในการเข้าห้องปฏิบัติการนอกเวลาทำการเป็นอย่างไร?
A9: ต้องสวมเสื้อกาวน์ปฏิบัติการ (Lab Coat), กางเกงขายาว, รองเท้าหุ้มส้นมิดชิด (หรือรองเท้า Safety), สวมแว่นตานิรภัย (Safety Glasses) และอุปกรณ์ป้องกันส่วนบุคคล (PPE) ตามข้อกำหนดเฉพาะของแต่ละห้องปฏิบัติการ

--------------------------------------------------------------------------------
[หมวดหมู่ 4: ลำดับขั้นตอนการอนุมัติ 4 ขั้นตอน (Sequential Approval Flow)]
Q10: ขั้นตอนการอนุมัติตามลำดับ 4 ขั้นตอน มีอะไรบ้าง?
A10: ลำดับการอนุมัติเป็นดังนี้:
- Stage 1: อาจารย์ที่ปรึกษา (Advisor) หรือหัวหน้าสาขาวิชา (กรณีเด็กนอกสาขา/บุคคลภายนอก)
- Stage 2: เจ้าหน้าที่ประจำแผนกวิชา (Division Staff) เพื่อตรวจความพร้อมของอุปกรณ์
- Stage 3: หัวหน้าห้องปฏิบัติการ (Lab Head) เพื่อตรวจตารางห้องและเครื่องมือเฉพาะ
- Stage 4: หัวหน้าอาคาร/ผู้ดูแลระบบ (Admin) เพื่ออนุมัติขั้นสุดท้ายและนัดบันทึกข้อมูลชีวมิติ

Q11: หากผู้อนุมัติใน Stage ก่อนหน้ายังไม่อนุมัติ คำขอจะส่งต่อไปยัง Stage ถัดไปหรือไม่?
A11: ระบบทำงานแบบ Sequential Flow จะไม่ส่งต่อไปยัง Stage ถัดไปจนกว่าขั้นตอนก่อนหน้าจะกด 'Approve' เสร็จสมบูรณ์

Q12: ในกรณีที่เป็นนักศึกษาต่างคณะหรือบุคคลภายนอก ใครจะเป็นผู้อนุมัติใน Stage 1?
A12: ระบบมีตรรกะตรวจจับอัตโนมัติ โดยจะส่งคำขอไปยัง "หัวหน้าสาขาวิชาวิศวกรรมโยธา" โดยตรงเป็นผู้อนุมัติใน Stage 1 แทนอาจารย์ที่ปรึกษาประจำสาขา

--------------------------------------------------------------------------------
[หมวดหมู่ 5: กระบวนการสำหรับผู้อนุมัติ (Approver Guide)]
Q13: ผู้อนุมัติต้องเข้าสู่ระบบเพื่อกดอนุมัติคำขออย่างไร?
A13: ผู้อนุมัติจะได้รับอีเมลแจ้งเตือนที่มีปุ่ม Quick Action "อนุมัติทันที (1-Click Approve)" และ "ปฏิเสธ" หรือสามารถกดลิงก์เข้าไปดูรายละเอียดคำขอแบบเต็มและตรวจสอบบทวิเคราะห์จาก AI บนหน้าเว็บก่อนตัดสินใจได้

Q14: การอนุมัติทางอีเมลมีความปลอดภัยหรือไม่ มีการป้องกันการสวมสิทธิ์อย่างไร?
A14: ปลอดภัยสูงมาก เนื่องจากระบบใช้ One-Time Secure Token ความยาว 64 ตัวอักษรที่สร้างด้วย Utilities.getUuid() สองชุด (ไม่ใช้ Math.random) บินด์อีเมลผู้อนุมัติตามขั้น (Admin ลัดได้เท่านั้น) มีวันหมดอายุ TOKEN_EXPIRY_DAYS และล็อกเมื่อพยายามผิด 5 ครั้ง — ทุก Log บันทึกแบบ maskToken() ไม่เปิดเผยค่าเต็ม

Q15: หากผู้อนุมัติกด 'Reject' (ปฏิเสธคำขอ) จะเกิดอะไรขึ้น?
A15: ระบบจะบังคับให้ระบุเหตุผลการปฏิเสธ จากนั้นสถานะของคำขอจะเปลี่ยนเป็น 'Rejected' ทันที และระบบจะส่งอีเมลแจ้งผู้ยื่นคำขอพร้อมระบุเหตุผลเพื่อให้นำไปแก้ไขยื่นใหม่

--------------------------------------------------------------------------------
[หมวดหมู่ 6: รหัส Access Code และความหมายของตัวเลข]
Q16: รหัส Access Code 6 หลักคืออะไร และสร้างขึ้นมาอย่างไร?
A16: เป็นรหัสประจำตัวสำหรับใช้กับระบบ Access Control ประตูห้องแล็บ ประกอบด้วย:
- หลักที่ 1: ประเภทผู้ใช้ (1=อาจารย์, 2=เจ้าหน้าที่, 3=ป.ตรี, 4=ป.โท, 5=ป.เอก, 6=ภายนอก)
- หลักที่ 2: รหัสแผนกวิชา (1-7 ตามโครงสร้างสาขาวิศวกรรมโยธา)
- หลักที่ 3-6: ลำดับที่ของคำขอที่รันต่อเนื่องแบบ Atomic Lock (เช่น 0001 ถึง 9999)

Q17: ผู้ยื่นคำขอจะทราบรหัส Access Code ของตนเองได้อย่างไร?
A17: Access Code จะถูกสร้างทันทีเมื่อยื่นคำขอสำเร็จ และจะปรากฏในอีเมลยืนยันการรับคำขอ รวมถึงในหน้าบัตรผ่านดิจิทัล (Digital Pass) เมื่อผ่านการอนุมัติครบ 4 ขั้นตอน

--------------------------------------------------------------------------------
[หมวดหมู่ 7: การบันทึกข้อมูลชีวมิติ (Biometric Appointment & Enrollment)]
Q18: เมื่อผ่านการอนุมัติ Stage 4 แล้ว ผู้ยื่นคำขอต้องทำอะไรต่อ?
A18: ผู้ยื่นคำขอต้องเดินทางมาบันทึกข้อมูลชีวมิติ (สแกนลายนิ้วมือ/ใบหน้า) ณ สำนักงานธุรการอาคารวิศวกรรมโยธา ตามวันและเวลาที่ระบุไว้ในอีเมลแจ้งผลการอนุมัติ

Q19: สิ่งที่ต้องเตรียมมาในวันนัดหมายบันทึกข้อมูลชีวมิติมีอะไรบ้าง?
A19: 1. บัตรนักศึกษา หรือบัตรประจำตัวประชาชนตัวจริง 2. หลักฐานการได้รับอนุมัติ (เปิดจากอีเมลหรือแสดง QR Digital Pass บนมือถือ)

Q20: การนัดหมายสแกน Biometric มีการแจ้งเตือนลงปฏิทินหรือไม่?
A20: มี ระบบจะสร้าง Google Calendar Event ลงในปฏิทินของ Admin และส่งเทียบเชิญ (Calendar Invite) ไปยังอีเมลของผู้ขอโดยอัตโนมัติ

--------------------------------------------------------------------------------
[หมวดหมู่ 8: ระบบวิเคราะห์คำขอด้วย AI (ORG AI Assistant)]
Q21: ระบบ AI ใน CE F.A.I.R. ทำหน้าที่อะไร?
A21: AI ทำหน้าที่อ่านวิเคราะห์รายละเอียดคำขอ วัตถุประสงค์ ช่วงเวลา ความสอดคล้องของหัวข้อวิจัย และตรวจสอบความเสี่ยง (เช่น การขอใช้ห้องดึกเกินไป) แล้วสร้างบทสรุปย่อ 4-5 บรรทัดให้ผู้อนุมัติอ่านประกอบการตัดสินใจได้อย่างรวดเร็ว

Q22: หากระบบเครือข่ายขัดข้องหรือไม่สามารถเชื่อมต่อ AI ได้ ระบบจะทำงานต่อได้หรือไม่?
A22: ทำงานได้ตามปกติ 100% เพราะระบบมี Fallback Algorithm แบบ Rule-Based วิเคราะห์ข้อมูลเบื้องต้นให้อัตโนมัติโดยไม่สะดุด

--------------------------------------------------------------------------------
[หมวดหมู่ 9: บัตรผ่านดิจิทัล (QR Code Digital Pass)]
Q23: QR Code Digital Pass คืออะไร และใช้งานอย่างไร?
A23: คือบัตรผ่านเข้าอาคารแบบดิจิทัลที่จะแสดงผลบนหน้าต่างติดตามสถานะเมื่อคำขอได้รับการอนุมัติ 'Approved' ครบ 4 ขั้นตอน สามารถใช้แสดงต่อเจ้าหน้าที่รักษาความปลอดภัย หรือสแกนเพื่อตรวจสอบความถูกต้องของสิทธิ์

Q24: ข้อมูลที่ถูกเข้ารหัสใน QR Code มีอะไรบ้าง?
A24: เข้ารหัสในรูปแบบ: CE-PASS:[เลขที่คำขอ]:[AccessCode]:[ชื่อผู้ได้รับอนุมัติ] เพื่อให้ง่ายต่อการตรวจสอบและป้องกันการปลอมแปลง

--------------------------------------------------------------------------------
[หมวดหมู่ 10: การเชื่อมต่อระบบควบคุมประตูและเครื่องสแกน (Hardware Webhook)]
Q25: ระบบส่งข้อมูลไปยังเครื่องสแกนประตูอย่างไรเมื่อคำขออนุมัติ?
A25: ระบบจะยิง Webhook (HTTP POST) ไปยัง API Gateway ของเครื่องสแกน พร้อมส่งข้อมูล AccessCode, ชื่อ-สกุล, ช่วงวันที่อนุญาต และรหัสห้อง เพื่อเปิดสิทธิ์การสแกนผ่านประตูอัตโนมัติ

Q26: เมื่อผู้ใช้สแกนนิ้วผ่านประตู ข้อมูลจะถูกบันทึกกลับมาที่ระบบหรือไม่?
A26: เครื่องสแกนจะยิง Webhook ขากลับมาที่ฟังก์ชัน doPost() ของระบบ เพื่อบันทึกประวัติการเข้า-ออก (Access Logs) ลงในชีต Logs เพื่อความปลอดภัยสูงสุด

--------------------------------------------------------------------------------
[หมวดหมู่ 11: การติดตามสถานะคำขอและการค้นหาข้อมูล]
Q27: ผู้ยื่นคำขอสามารถติดตามสถานะคำขอของตนเองได้อย่างไร?
A27: สามารถทำได้ 2 วิธี: 1. คลิกปุ่ม 'ติดตามสถานะคำขอ' ในอีเมลที่ได้รับ 2. เข้าหน้าเว็บแล้วไปที่แท็บ 'แดชบอร์ด / ติดตามสถานะ' จากนั้นค้นหาด้วยเลขที่คำขอ (Request ID), อีเมล หรือเบอร์โทรศัพท์

Q28: หากต้องการยกเลิกคำขอที่ส่งไปแล้ว ต้องทำอย่างไร?
A28: ให้ติดต่อเจ้าหน้าที่ดูแลระบบ (Admin) หรือแจ้งอาจารย์ที่ปรึกษาให้กด 'Reject' คำขอนั้น พร้อมระบุว่าผู้ขอยกเลิกความประสงค์

--------------------------------------------------------------------------------
[หมวดหมู่ 12: การจัดการห้องปิดปรับปรุง (Room Closures)]
Q29: หากห้องปฏิบัติการปิดซ่อมบำรุง ระบบจะแจ้งเตือนผู้ขออย่างไร?
A29: เมื่อผู้ใช้เลือกห้องและช่วงวันที่ตรงกับการปิดปรับปรุง (Room Closures) ระบบจะแจ้งเตือนบล็อกทันทีว่าห้องดังกล่าวปิดใช้งานตั้งแต่วันที่ใดถึงวันที่ใด

Q30: ใครเป็นผู้มีสิทธิ์เพิ่มหรือแก้ไขรายการปิดปรับปรุงห้องปฏิบัติการ?
A30: ผู้ดูแลระบบ (Admin) หรือหัวหน้าห้องปฏิบัติการ สามารถจัดการตารางปิดปรับปรุงได้ผ่านชีต RoomClosures
================================================================================

[หมวดหมู่ 13: การตั้งค่าระบบและการดูแล Backend]
Q31: ระบบใช้ฐานข้อมูลอะไร?
A31: ใช้ Google Sheets เป็นฐานข้อมูลหลัก โดย `initDatabase()` จะสร้างหรือเติม headers ของชีต Users, Advisor, DivisionStaff, LabHead, Admin, Rooms, Requests, RoomClosures, Settings และ Logs ให้ครบตาม schema

Q32: หากชีตหรือคอลัมน์บางส่วนหายไป ต้องทำอย่างไร?
A32: ให้ผู้ดูแลรัน `initDatabase()` ระบบจะสร้างชีตที่ไม่มีและเติมเฉพาะ headers/Settings ที่ขาด โดยไม่เปลี่ยนสถาปัตยกรรม frontend

Q33: ค่า ORG_API_KEY ต้องเก็บที่ใด?
A33: ต้องเก็บใน Script Properties ของ Apps Script เท่านั้น ห้ามใส่ค่าจริงใน Code.gs, README, chatbot knowledge base หรือไฟล์ที่ commit เข้า repository

Q34: ระบบใช้เขตเวลาใด?
A34: ค่าเริ่มต้นคือ `Asia/Bangkok` และมี key `TIMEZONE` ใน Settings สำหรับระบุเขตเวลาที่ใช้ประมวลผลวันเวลา

Q35: ระบบมีโหมดปิดปรับปรุงหรือไม่?
A35: มี key `MAINTENANCE_MODE` ใน Settings ค่าเริ่มต้น `FALSE` ผู้ดูแลสามารถใช้เป็น flag สำหรับควบคุมการเปิดให้บริการตามนโยบายของระบบ

Q36: อายุ token อนุมัติกี่วัน?
A36: ค่าเริ่มต้นคือ 7 วันจากเวลาที่สร้าง token และควบคุมด้วย `TOKEN_EXPIRY_DAYS` ใน Settings

Q37: ระบบส่งอีเมลเตือนผู้อนุมัติซ้ำเมื่อใด?
A37: ใช้ค่า `APPROVAL_REMINDER_DAYS` ค่าเริ่มต้น 3 วัน และทำงานผ่าน time-driven trigger `sendPendingApprovalReminders()`

Q38: ระบบอัปเดตคำขอหมดอายุอย่างไร?
A38: ฟังก์ชัน `updateExpiredRequests()` ทำงานตาม trigger รายวัน เพื่อเปลี่ยนคำขอที่ถึงวันเริ่มเป็น Active และคำขอที่เลยวันสิ้นสุดเป็น Expired ตามเงื่อนไขของระบบ

Q39: Running Number ของ Request ID ปลอดภัยจากการชนกันหรือไม่?
A39: ระบบใช้ `LockService.getScriptLock()` ครอบการอ่านและเขียน sequence จึงลดความเสี่ยงเมื่อมีหลายคำขอเข้าพร้อมกัน

Q40: Running Number ของ Access Code เริ่มต้นอย่างไร?
A40: Settings เริ่มที่ `0500`; การสร้างครั้งแรกจะได้ running number `0501` และเมื่อถึง `9999` จะวนกลับไป `0501` โดยใช้ Script Lock

[หมวดหมู่ 14: Frontend และการใช้งานระบบ]
Q41: ระบบ frontend ใช้โครงสร้างกี่แท็บ?
A41: ใช้โครงสร้าง 2 แท็บเดิม ได้แก่ `ยื่นคำขอ` และ `แดชบอร์ด` ตามแนวคิด Clean 2-Tab Design ไม่ได้เปลี่ยนเป็น 5 views

Q42: ระบบมี hash routing แบบ #request, #status, #approve หรือไม่?
A42: ไม่มีการเพิ่ม hash routing 5 เส้นทาง ระบบใช้การสลับแท็บด้วย Vue state และรองรับ `#dashboard` เป็นทางกลับแดชบอร์ดจากลิงก์บางส่วน

Q43: Approve View เป็นหน้าแยกหรือไม่?
A43: ไม่ใช่หน้าแยก การอนุมัติใช้ `ReviewModal` ภายใน Dashboard โดยเปิดจาก token และเลือก read-only เมื่อเป็นการติดตามสถานะ

Q44: ผู้อนุมัติเปิดคำขอจากอีเมลได้อย่างไร?
A44: ลิงก์อีเมลส่ง `token` และ `stage` มายัง Web App; backend ตรวจ token ก่อน แล้วเปิด Dashboard พร้อม ReviewModal หรือดำเนินการ one-click ตามประเภท action

Q45: StatusBadge ใช้ทำอะไร?
A45: เป็น Vue reusable component สำหรับแสดงสถานะ เช่น Approved, Pending, Rejected, Skipped, Active และ Expired ด้วยสีที่สื่อความหมายสอดคล้องกัน

Q46: RoomCard ใช้ทำอะไร?
A46: เป็น component สำหรับแสดงข้อมูลห้องแบบ card ได้แก่ รหัสห้อง ชื่อ อาคาร ชั้น ความจุ สิ่งอำนวยความสะดวก รูปภาพ และสถานะห้อง

Q47: ModalConfirm ใช้ทำอะไร?
A47: เป็น modal ยืนยันการกระทำที่นำกลับมาใช้ซ้ำได้ มีปุ่มยืนยัน/ยกเลิก และไม่ผูกกับ view ใด view หนึ่ง

Q48: TimelineStep และ LoadingSpinner ใช้ทำอะไร?
A48: `TimelineStep` ใช้แสดงแต่ละขั้นของ approval flow ส่วน `LoadingSpinner` ใช้แสดงสถานะกำลังประมวลผล รวมถึงข้อความที่เปลี่ยนหลังรอเกิน 4 วินาที

Q49: ผู้ใช้เปิดระบบจากมือถือได้หรือไม่?
A49: ได้ เนื่องจาก Index.html และ Stylesheet.html ใช้ responsive layout รองรับคอมพิวเตอร์ แท็บเล็ต และสมาร์ทโฟน

Q50: หลังแก้ config ต้องทำอะไรเพื่อ deploy?
A50: ตรวจสอบ `appsscript.json`, รัน `initDatabase()` และ `setupDailyTriggers()` ตามความเหมาะสม ตั้งค่า Script Properties/Settings แล้ว deploy Web App ใหม่พร้อมยอมรับ OAuth scopes ที่ระบบร้องขอ
